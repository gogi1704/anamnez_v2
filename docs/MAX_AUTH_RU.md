# Авторизация пользователей через MAX

## Что реализовано в Консилиуме

Сервер Консилиума готов принимать от доверенного MAX-бота MAX ID и постоянный
числовой `chel_id`, выпускать одноразовую ссылку и создавать защищённую сессию.
Ссылка действует 7 дней и после первого использования становится
недействительной.

Сам проект `anketa_bot_max` не изменён. Чтобы кнопка появилась в боте, его
разработчику позднее потребуется вызвать описанный ниже API и поместить
возвращённый `auth_url` в `LinkButton`.

Консилиум хранит постоянную привязку:

```text
provider=max + MAX ID → chel_max_000000001234
```

После перехода создаётся отдельная серверная сессия на 90 дней. Cookie содержит
не `chel_id`, а случайный идентификатор сессии. На другом устройстве пользователь
получает через того же MAX-бота новую сессию прежнего профиля.

## Настройка общего секрета

Создайте случайный секрет на сервере:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Одно и то же значение указывается:

- в Консилиуме: `BOT_INTEGRATION_SECRET`;
- в MAX-боте: `CONSILIUM_BOT_SECRET`.

Секрет не передаётся браузеру и не должен храниться в Git.

## Настройки Консилиума

```env
PUBLIC_BASE_URL=https://consilium.example.ru
BOT_INTEGRATION_SECRET=СЛУЧАЙНЫЙ_СЕКРЕТ
AUTH_LINK_TTL_SECONDS=604800
SESSION_TTL_DAYS=90
SESSION_COOKIE_NAME=consilium_session
COOKIE_SECURE=1
```

## Настройки MAX-бота

```env
CONSILIUM_API_URL=https://consilium.example.ru
CONSILIUM_BOT_SECRET=ТОТ_ЖЕ_СЛУЧАЙНЫЙ_СЕКРЕТ
CHEL_ID_DATABASE_PATH=/var/lib/anketa-bot/chel_id.db
CHEL_ID_IMPORT_FROM_SHEETS=0
```

Каталог `/var/lib/anketa-bot` должен быть постоянным Docker volume или
серверным каталогом с резервным копированием. Нельзя хранить основную базу
идентификаторов только во временном слое контейнера.

## API-контракт для будущего подключения бота

Запрос выполняется сервером бота, а не браузером:

```http
POST /api/auth/max/link
Authorization: Bearer ОБЩИЙ_СЕКРЕТ
Content-Type: application/json

{
  "max_user_id": 4392901,
  "chel_id": 12854
}
```

Успешный ответ:

```json
{
  "auth_url": "https://consilium.example.ru/auth/max?t=ОДНОРАЗОВЫЙ_ТОКЕН",
  "expires_at": "2026-07-25T12:05:00+00:00"
}
```

## Первый вход после будущего подключения

1. MAX сообщает боту подтверждённый `user_id`.
2. Бот получает существующий или создаёт новый числовой `chel_id`.
3. Бот вызывает `POST /api/auth/max/link` с серверным секретом.
4. Консилиум создаёт одноразовый непрозрачный токен сроком на 7 дней.
5. Бот показывает `LinkButton` «Открыть Консилиум».
6. Переход на `/auth/max?t=...` обменивает токен на Secure/HttpOnly cookie.
7. Браузер перенаправляется на `/`, поэтому токен исчезает из адресной строки.

Маршрут обмена не записывает токен в журналы: приложение заменяет его на
`[REDACTED]`, а Nginx отключает access-log только для `/auth/max`.

## Повторный вход и другое устройство

- Пока cookie действует, сайт узнаёт пользователя напрямую.
- После очистки cookie пользователь снова нажимает `/start` в MAX.
- На другом устройстве он делает то же самое.
- Новый токен и новая сессия всегда указывают на прежний `chel_id`.
- Старая анкета и диалоги сохраняются.
- Если неиспользованная ссылка старше 7 дней, бот должен запросить новую.

## «Начать заново»

Для авторизованного MAX-пользователя сброс удаляет анкету, диалоги, память,
симптомы и обращения, но сохраняет MAX-привязку, серверные сессии и `chel_id`.
Для анонимного пользователя по-прежнему создаётся новый `chel_id`.

## Ограничение доступа

В `external_identities.access_status` поддерживается состояние `active`. Если
его изменить на `blocked`, сервер перестанет выдавать новые ссылки этому
MAX-пользователю. Перед публичным запуском следует добавить административный
интерфейс для статусов `pending`, `active`, `blocked` и срока доступа.

## Проверка

После запуска:

1. Нажмите `/start` и откройте кнопку.
2. Заполните имя в анкете.
3. Очистите cookie или откройте другой телефон.
4. Снова нажмите `/start`.
5. Убедитесь, что загрузился прежний профиль.
6. Повторно откройте старую одноразовую ссылку — сервер должен вернуть ошибку.
